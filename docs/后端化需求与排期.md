# Multi-document 后端化：需求完善与开发排期

> 2026-10-21 起草。基于源码通读（非页面观察）得出，所有"现状"均可在代码中定位。
> 目标：周四（10-22）下班前本地跑出核心功能；周五（10-23）交付能用版本；后续 Docker 化。

## 一、现状功能盘点（代码事实）

### 前台（访客侧，无需登录）
| 功能 | 实现位置 |
|---|---|
| 文档总首页：多项目入口，各项目产品数/可见文档数 | `src/app/page.tsx` |
| 项目文档中心（独立访问链接） | `src/app/projects/[projectSlug]/` |
| 产品首页：目录 + 产品介绍 + 媒体（图/视频）+ 分类导航 | `products/[productSlug]/page.tsx` |
| 文档阅读页：多级目录、代码高亮、多语言代码标签、复制全文、收藏、二维码分享、上/下篇 | `docs/[docId]/page.tsx` + `MarkdownRenderer` |
| 全站搜索、收藏夹 | `api/search`、`favorites/` |

### 后台（admin，账号登录）
| 功能 | 实现位置 |
|---|---|
| 登录/会话（账号密码 + cookie session） | `api/admin/auth/*`、`lib/auth.ts` |
| 项目、产品、目录树管理 | `api/admin/projects`、`catalog`、`tree/update` |
| 文档库：Markdown 编辑器 + 26 种内容组件 | `api/admin/library`、`lib/editor.ts` |
| 草稿 / 发布双状态，发布生成版本快照与变更摘要 | `api/admin/docs/save`、`publish`、`lib/documents.ts` |
| 一份文档挂多个项目/目录（placements） | `DocPlacement` |
| 用户管理：3 预设角色 + 自定义角色，8 种权限，按用户覆盖 | `api/admin/users`、`roles`、`lib/authTypes.ts` |
| 媒体上传 | `api/admin/uploads`、`lib/uploadMedia.ts` |

### 数据层（问题根源）
- **所有数据存单文件 `data/store.json`**（当前 1230 行起步，随文档/历史线性膨胀）
- `getStore()` 每次请求**全量读盘并 JSON.parse**；`saveStore()` 临时文件 + rename 原子写，**但无锁、无事务**
- 并发控制仅靠 `updatedAt` 字符串比对，冲突时提示用户"导出正文手动合并"
- 版本历史（DocRevision）与文档正文、用户、角色挤在同一个文件里

**结论：业务功能已相当完整，"效果差"不是功能缺失，是数据层撑不住——这正是后端化要解决的全部。**

## 二、需求完善（后端化范围）

### 核心（周四必须通）
1. 文档 CRUD：草稿/发布两态、Markdown 正文、外观配置
2. 版本链：每次发布落一条不可变快照（版本号、标题、内容、变更摘要、发布时间）
3. 目录树：产品内多级目录、排序、隐藏
4. 乐观锁升级：由时间戳比对改为 `version` 列自增比对（数据库层防覆盖）

### 辅助（随之迁移）
5. 项目 / 产品 / 文档多项目挂载关系
6. 用户 / 角色表化（**最简平移**：结构照现有 RoleDefinition，不做新功能——原口径"不着急"，但用户数据也在 store.json 里，不迁就没法切库，故纳入周五）

### 不做（明确出范围）
- 搜索引擎化（继续 SQL LIKE，量级没到）
- 工作流/审批（无需求信号）
- 媒体文件进库（继续文件系统 + 目录，仅后置考虑元数据表）

## 三、数据库设计（MySQL 8，9 张表）

```
projects          项目（id, slug, name, description, brand…, updated_at）
products          产品（id, code, name, category_id→categories, description）
categories        产品分类（id, name）
project_products  项目-产品绑定（project_id, product_id, group, media JSON, unique 双键）
doc_categories    文档目录树（id, product_id, parent_id 自关联, name, icon, sort, hidden）
documents         文档主表（id, product_id, slug, title, description,
                  content MEDIUMTEXT, status ENUM(draft,published),
                  version INT, hidden, appearance JSON, updated_at,
                  unique(product_id, slug)）
doc_revisions     历史表（id, doc_id, version, title, content,
                  summary, changes JSON, placements JSON, published_at,
                  baseline BOOL, created_by, unique(doc_id, version)）
doc_placements    文档挂载（doc_id, project_id, product_id, category_id）
admin_users       后台用户（id, username, name, role_id, password_hash,
                  status, last_login_at）
roles             角色（id, name, description, permissions JSON）
```

设计要点：
- **文档与历史分离**：`documents` 只存当前态，历史全量进 `doc_revisions`——这是你说的"历史表"，也是解决"文件越滚越大"的关键
- 草稿即 `documents.status='draft'`，发布时同事务内更新主表 + 插入 revision（替代现在两份 map 的做法）
- `content` 用 MEDIUMTEXT（16MB 上限，远超单篇文档需要）

## 四、技术决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| 数据库 | **MySQL 8** | 用户熟悉优先；本项目纯 CRUD + 树查询，用不到 PG 特性，语法差异不构成风险 |
| ORM | **Prisma** | schema 即表结构文档、migration 工具齐、TS 类型自动生成，与现有 TS 代码零缝 |
| 前后端 | **保持 Next.js 全栈，只换数据访问层**（暂不拆独立后端） | API 路由已是 REST 形态（`/api/admin/*`），将来要拆只需平移路由层；两天工期内拆分风险不可控 |
| Docker | 后置到周五下午 | 单镜像 Next（含 API）+ MySQL 容器，docker-compose 一键起 |
